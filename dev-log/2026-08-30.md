# 개발 보드 교체

1. 문제

STM32H743VIT6보드의 SRAM이 최대 1 MB여서, 16bit, 44.1khz, 2채널 오디오 포맷으로는 최대로 녹음 가능한 오디오 길이가 $$ 16*44100*2 = 1411200 bit/s = 176400 byte/s, \frac{1 Mb}{176400 byte/s} \approx 5.9s $$이다. 트랙 하나만 관리한다면 괜찮지만, 향후 여러 개의 트랙을 동시에 재생할 때 약 5.9초의 재생 가능 시간을 트랙 수만큼 나누어야 하며 오디오 데이터만 저장하는 것이 아니라 메모리를 더 요구하는 FX를 적용할 수 있으므로 기존에 사용하는 개발 보드로는 메모리가 부족하다.

2. 분석

이전에 AI를 사용해 오디오 패스스루를 구현할 때 메모리 크기에 대해 질문하는 과정에서 메모리 크기로 인해 FX마다 구현 난이도가 다를 것이라고 판단했다. LPF나 EQ는 차분방정식으로 쉽게 처리를 할 수 있지만, Delay나 Reverb는 알고리즘 상 많은 메모리를 필요로 한다. 

AI에게 기존 개발 보드로는 메모리가 한계에 다다를 것 같다는 문제 상황을 제시했더니 기존 개발 보드의 SRAM으로는 한 트랙 정도는 구현 가능할지 몰라도, 여러 트랙까지 확장할 계획을 그리고 있는 상황으로는 한계에 부딪친다며, 메모리를 확장하는 것이 필요하다고 제안했다. 개발 보드에는 FMC가 존재하므로, 메모리 칩을 사서 연결할 수 있다고 한다.

3. 가설 검증

먼저 AI에게 기존 개발 보드로 메모리를 확장한다면 어떤 메모리를 확장할 수 있을지 질문했고, SRAM, SDRAM, SD카드로 확장하는 방법을 얻었다. 

먼저, 각 방법을 금전적, 시간적, 용량 크기, 읽기 속도 등 다양한 기준으로 비교하여 아래와 같이 판단했다.

| 기준 | SRAM | SDRAM | SD카드 |
|---|---|---|---|
|금전적(1MB당 가격)|22,495원/MB|125원/MB|0.98원/MB|
|시간적|구매해야 함|구매해야 함|갖고 있어서 바로 쓸 수 있음|
|용량 크기|1MB|32MB|16GB|
|대역폭|약 200 MB/s|약 332 MB/s|약 80~98 MB/s|
|지연 시간|약 10 ns|약 18~33 ns|수백 µs~1ms 이상|

대역폭과 지연 시간을 보면 SRAM이나 SDRAM을 쓰는게 좋다. 특히 실시간 DSP에서는 지연 시간이 가능한 짧아야 하므로 SD카드는 쓰기 어렵다고 판단했다. SRAM은 금전적, 용량 크기 기준에서 1MB당 비용이 비싸기 때문에 쓰기 어렵다고 판단했다. 그러므로 SDRAM을 쓰는 것이 맞다고 판단했다.

4. 해결

그 다음으로는 AI에게 SDRAM을 어떻게 개발 보드와 연결해야 사용할 수 있을지 질문했는데, SDRAM 메모리 칩을 구매 후 PCB에 실장하여 개발 보드와 연결하거나, SDRAM 칩을 개발 보드에 실장하는 것 두 가지 방법을 얻었다. 구매하고자 하는 SDRAM의 가격은 개당 2천원 이상 정도여서 PCB에 직접 납땜하여 올리는 방법을 고민했지만, 납땜이 잘못되면 새로 PCB를 주문해야하는 것 때문에 루프스테이션 개발에 지장을 줄 수 있다고 판단하였고, 개발 보드에 장착되어 판매되는 모델로 구입하는 것을 선택했다.

가능하면 STM32H743VIT6을 MCU로 사용하는 보드를 구입하여 핀 재할당 문제를 피하려 했지만, 그러한 제품을 알리 익스프레스에서 찾을 수 없었다. 비슷한 시리즈의 다른 제품으로 찾아보았고, STM32H743IIT6을 MCU로 쓰는 FK743M2-IIT6를 선택했다. W9825G6KH-6 SDRAM을 장착하고 있어서 바로 사용할 수 있다고 판단했다. 

5. 결과

주문을 넣었고 부품이 도착하려면 일주일은 넘어야 해서 그동안 만능 기판에 납땜을 하거나, C 코드들을 C++로 개선하는 작업을 진행할 계획이다.

# C++ 개선 

1. 문제

개발할 때 일종의 객체 지향적 프로그래밍을 위해 구조체에 함수 포인터 멤버를 담아 정의한 후 모듈 함수에 구조체를 넘겨서 객체의 메서드를 호출하는 패턴을 사용했다. 그러나 캡슐화를 하지 못하므로 완전한 객체 지향은 아니다. 

그리고 enum을 적극적으로 사용했는데, 타입을 검사하지 않고 enum을 쓸 수 있다. UiStateId를 받도록 했는데 아무 정수나 넣어도 컴파일 에러가 발생하지 않는다. 

구조체를 정적으로 선언할 때 실수로 멤버 초기화를 빠뜨릴 수 있다.

2. 분석

AI에게 프로젝트 코드를 읽어보라고 시키고 C++로 전환했을 때 개선될 부분과 C만으로도 개선될 부분을 살펴보라고 했다. 개발할 때 느꼈던 점들은 C++로 전환했을 때 개선된다고 한다. 

AI는 패널, 파라미터, FX 종류가 점점 늘어날 경우 C로는 비슷한 코드가 반복되어 확장에 불편하니 C++의 이점을 살리면 좋다고 한다. 특히 현재 검증 코드에서는 런타임에 검증을 하는 것도 문제고 잘못된 enum 사용도 잡아내지 못하는 점이 문제이므로 이것도 C++로 개선 가능하다고 한다. 

그러나 C로도 충분히 개선될 부분들이 많다. config 매크로 대신 정적 배열, 모든 상태를 context로 이동, 상태 관리 태스크가 갖는 과도한 책임을 분리 등. 

3. 가설 검증

AI가 C++로 전환할 때 실제로 개선되는 부분과 꼭 그렇지 않은 부분을 제시했는데 각각의 이유를 살펴봤다.

- 코드가 너무 방대해져서 고쳐야 한다?

코드 줄 수를 따져보면 약 4000줄이라고 한다. 반복되는 코드도 있기 때문에 실질적인 코드 양은 더 적을 것이므로 관리가 안되는 수준은 아니다.

- C의 문법적 한계 때문에 바꿔야 하나?

C++에서도 정적으로 변수를 선언하면 초기화를 해야하고, 누락될 수 있다. 또한 런타임 단계에서 검증하던 코드들을 컴파일 단계로 이동시키는 것이 C++에서만 가능하진 않다.

단, enum 타입 검사가 강하게 이뤄지지는 않는 점, 구조체 초기화가 제대로 이뤄지지는 않는 점들을 생각해보면 C++ 문법으로 해결이 가능한 점이 있다.

- 모든 코드를 바꿔야 하나?

`extern "C"`와 같이 C++을 쓰면서 C 코드를 컴파일할 수 있다. 그러므로 HAL 라이브러리 코드, u8g2, FatFs 코드를 굳이 바꿀 필요는 없다. CubeMX에 의해 생성된 코드는 그냥 둔다.

- 결론

C++이 지원하는 객체지향 특성을 사용해서 C 문법으로 구현된 지저분한 코드들을 개선할 수는 있다. 그러나 C와 C++이 비슷한 점이 많으므로 C에서 발생한 문제가 C++에서도 발생할 수는 있다는 점을 주의해야한다.

C++로 개선은 하더라도 여러 잘못된 부분들(config 매크로 대신 정적 배열, 모든 상태를 context로 이동, 상태 관리 태스크가 갖는 과도한 책임을 분리 등)은 리팩토링이 필요하다. 이 점은 C++로 바꾼 이후에 판단해도 늦지 않다.
