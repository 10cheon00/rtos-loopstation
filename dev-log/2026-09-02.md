# Mcp23017Driver 구현 과정

1. 문제

C++로 리팩토링하는 첫 번째 작업으로, 가장 사이드 이펙트가 적은 드라이버 코드들을 수정하기로 했다. 기존 코드는 드라이버 모듈이 아니라 API만 제공하기 때문에 그때그때 필요한 함수를 호출한다는 느낌이 강했다. C 스타일로 구현되어 있었기 때문에 이를 C++ 스타일로 수정하여 드라이버 객체를 제공해야한다고 생각했다. 

문제는 드라이버 클래스를 정의한다면 누구나 만들 수 있다는 것이다. 하나의 I2C 페리퍼럴을 다루는 드라이버이므로 인스턴스가 여러 개라면 동시에 접근할 때 예상치 못한 문제가 생길 수 있다.

2. 분석

드라이버가 여러 개일 때 이 문제가 발생한다고 생각했고 싱글톤을 쓰면 이 문제가 해결된다고 생각했다. 그러나 드라이버 안에서 I2C 핸들을 알고 있어야 하고, 이 핸들을 누가 주입시켜주냐는 문제가 있었다. 그리고 드라이버를 여러 곳에서 동시에 쓸 때 한 번에 한 주체만 쓸 수 있도록 뮤텍스를 사용했었는데, 뮤텍스 관리의 주체가 태스크인지 드라이버인지도 모호했다. 기존 코드는 태스크가 직접 관리했다.

AI는 싱글톤의 초기화 과정을 세 가지로 나누었다. 

a. C++ 싱글톤 객체 생성 (메모리 할당)

    디자인 패턴을 따라 구현하면 GetInstance()의 static 지역 변수로 생성하거나, static 멤버 변수로 생성하게 된다. 

b. 드라이버 구성 (I2C 핸들과 뮤텍스 연결)

    객체가 생성된 이후 누군가 싱글톤에 접근하여 I2C 핸들과 뮤텍스를 주입한다. 단, 바로 초기화를 하지는 않는다.

c. Mcp23017 초기화 (실제 페리퍼럴 통신)

    싱글톤이 제공하는 기능들을 사용해 실제로 페리퍼럴을 제어할 때 하드웨어 초기화가 되지 않았는지 내부 상태를 확인하고 초기화를 수행한다.

그리고 주입했던 뮤텍스는 싱글톤이 직접 사용하는게 아니라 RAII를 준수하는 객체를 이용하도록 제안했다.  클래스 생성자와 소멸자에 osMutexAcquire, osMutexRelease를 호출하여 객체 생성과 소멸에 따라 뮤텍스를 획득, 반환하는 패턴이다.

3. 가설 검증

사실 검증할게 딱히 없었다. *드라이버 구성*에서 제안했듯 최초로 I2C 핸들과 뮤텍스를 주입해야하는 것은 시스템 상태 머신의 초기화 상태에서 수행할 것이고(실제로도 그렇게 해야하지만 일단 돌아가는 것이 먼저이므로 그렇게 하지 않았다), *Mcp23017 초기화* 단계는 이미 비슷한 방식으로 구현되어 있으니 이식하기만 하면 된다. *싱글톤 객체 생성*은 웹에 있는 자료를 참고하여 이해했다.

뮤텍스를 갖는 객체를 하나 만들어 생성자와 소멸자에서 획득, 반환하는 RAII 패턴도 처음 알게 되었는데, 공부가 부족함을 느꼈다.

FreeRTOS의 공식문서에서는 라이브러리 코드에서 뮤텍스를 사용할 때 발생하는 재귀 데드락에 대해 소개했는데, 여기서도 그 문제가 발생하는 것이 아닌가 생각했다. 재귀 뮤텍스가 발생하는 상황은 라이브러리 내에서 뮤텍스를 소유한 후 같은 라이브러리의 다른 함수를 호출할 때 그 함수 내에서 같은 뮤텍스를 또 소유하려는 것이다. 

뮤텍스를 소유한 후에는 뮤텍스를 소유하지 않는 API만 호출하는 규칙을 두면 해결된다고 생각했다. 다르게 말하면 public으로 공개된 함수만 한 번 획득하고, 내부 함수들에선 뮤텍스를 획득하지 않도록 하면 된다. 

AI는 I2C를 혼자 사용하는 전용 태스크를 두는 방법이 가장 낫다고 한다. 공식문서에서도 자원을 혼자 갖는 태스크가 가장 이상적인 상호 배제 해결법이라고 했다. 하지만 메시지 형식 및 필요한 코드가 늘어나기 때문에 현재 단계에서는 이득이 크지 않다고 한다.

4. 해결

외부에서는 Mcp23017Driver::GetInstance()를 통해 싱글톤에 접근하여 바로 API를 사용할 수 있게 제공했다. 이렇게 하니, input_task와 display_task에서 hi2c와 i2c_mutex를 initparams로 받지 않게 되었다. 드라이버에 최초 주입만 해주면, 외부에서는 어떤 페리퍼럴을 쓰는지 알지 않아도 되었다.

5. 결과

컴파일 결과 오류는 없지만, 아직 리팩토링이 완료되지 않아 테스트를 진행하진 못했다.

# EnumMap 구현 과정

1. 문제

C 환경에서 개발할 땐 설정을 저장할 배열을 만들고, enum을 인덱스로 사용한 인덱스 지정 초기화로 값을 주입했다. 이걸 고치려고 C++로 전환했다고 해도 될만큼 다소 원시적인 방법이다. 이 방식의 문제점은 배열 초기화 및 사용에는 문제가 없지만 나중에 검증을 하려고 하면 각 설정마다 배열 타입이 제각각이라 관리하기가 번거롭다. 게다가 검증을 위해서는 공용 알고리즘을 통과해야하는데, 설정마다 타입이 다르므로 알고리즘을 구현하기 까다롭다고 생각했다. 기존에는 매크로를 사용하여 검증자에 자동 등록하도록 했는데, 매크로에 의해 배열 선언 코드가 가려져 코드 이해가 쉽지 않다는 문제도 있다.

2. 분석

위와 같은 이유, 그리고 확장과 유지보수의 어려움이 예상되어 C++로 전환하기로 했다. 

확장자를 변경한 후 naming mangling 문제를 해결하고, 그대로 컴파일했더니 C++ 에서는 인덱스 지정 초기화가 안되는 것을 알았다. AI에게 인덱스 지정 초기화 방식을 사용할 수 있는 C++ 코드 예시를 보여달라고 했고, std::array를 사용한 코드 예시를 얻었다. 일단 컴파일이 되도록 하기 위해 해당 코드 작성 패턴을 컴파일 에러가 발생하는 곳에 적용했다.

```cpp
static constexpr auto track_state_idle_transition_table = [] {
    std::array<TrackStateId, TRACK_ACTION_ID_COUNT> values{};
    values[TRACK_ACTION_ID_NONE] = TRACK_STATE_ID_IDLE;
    values[TRACK_ACTION_ID_ENTER_RECORD_PLAY] = TRACK_STATE_ID_RECORDING;
    values[TRACK_ACTION_ID_ENTER_STOP] = TRACK_STATE_ID_IDLE;
    return values;
}();
```

그러나... 코드의 절반은 설정값, 나머지는 문법을 위한 코드여서 이를 제거해야함을 깨닫고 AI에게 개선 방법에 대해 질문했다. enum을 인덱스로 사용해 배열에 접근해서 설정값을 얻는 것은 Map과 유사하므로 std::map을 흉내내되 배열을 사용하는 ArrayMap을 구현하되, 이 클래스를 사용하여 설정 객체를 초기화할 때 어떤 패턴으로 사용하고 싶다는 예시를 포함해 물어봤다.사용 예시와 함께 3가지 초기화 방법을 검토해달라고 했다.

3. 가설 검증

AI는 3가지 초기화 방법을 각각 이렇게 평가했다.

- 외부에서 초기화된 array를 생성자에 주입하는 것 

    C++에서 흔히 볼 수 있는 패턴. 그러나 설정 관계가 바로 드러나는 요구사항과 적합하지 않음.

- 가변 인자(va_args)를 사용하되 C++ 문법으로 생성자를 구현하는 것

    C 스타일 가변 인자는 C++에서 사용하지 않는 편이 좋음. 컴파일 시기에 인자를 검사할 수 없음.

- Pair 구조체 배열을 생성자에 주입하는 것

    데이터와 자료구조 생성을 분리해야한다면 괜찮은 방법. 그러나 데이터 선언과 자료구조 선언이 분리되므로 설정 객체 생성 코드가 길어짐.

AI는 사용 예시에 가장 적합한 방식은 가변 템플릿 생성자라고 알려주었다. 그리고 생성 시 constexpr, explicit 키워드를 사용하여 명시적 형변환과 컴파일 시기에 식을 평가하는 방법을 알려주었다. 그리고 컴파일 시기에 형변환 오류를 잡아주는 static_cast도 알게 되었다. 이 답변을 듣고 나서 C++ 문법에 대한 공부가 부족함을 느꼈다.

4. 해결

템플릿을 사용한 EnumMap를 구현했고, 기존에 ConfigTable 매크로를 사용했던 설정 파일들을 전부 EnumMap을 사용한 고정 크기 Map으로 교체했다. 설정 검증은 리팩토링이 완료된 이후 진행하기로 미루었다.

5. 결과

컴파일 결과 오류가 없다. 기존 코드는 ENTRY를 먼저 선언 후 테이블 생성 시 ENTRY를 등록하는 코드여서 생성과 설정 관계가 나뉘어 있었지만 EnumMap을 사용하는 코드에는 생성 시 초기화가 된다.
