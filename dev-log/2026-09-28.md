# PM 봇과 단절

PM 봇을 구현했던 이유는 프로젝트 일정 관리를 해줄 것을 기대했기 때문이다. 하지만 원하는만큼 일정 관리를 잘 해주지 못했고, 프로젝트와 관련된 자료를 만들어서 넘겨주는 것보다 그냥 내가 직접 일정을 관리하는 것이 더 쉬웠다. 그래도 제대로 쓸 수 있을만큼 구축은 해봐야겠다. 저번엔 그냥 코덱스한테 해달라고 해서 슬랙 봇 구현정도만 했기 때문에 여기에 살만 좀 더 붙이면 될 것 같다.

# 시스템 태스크 추가

예전에 시스템이 최초로 시작될 때 드라이버들을 초기화하는 작업을 제일 먼저 하기로 했는데 이 작업을 상태 관리 태스크에 두자니 역할이 늘어나는 것 같아 분리하려고 했다. 스케줄러는 이 태스크를 제일 먼저 시작하고 태스크가 종료되기 전까지는 다른 태스크들이 실행되면 안된다. 이 제약을 구현하기 위해 다른 태스크들의 시작을 멈추려고 헀으나 태스크 생성에 관한 코드들은 모두 CubeMX가 자동 생성하고 있기 때문에 태스크 시작 자체는 멈출 수 없었다. 

여기서 AI에게 다른 태스크들을 강제로 정지시킨 후 초기화가 끝났을 때 시작시키는 방법과 시스템 태스크의 우선순위를 최대로 올리는 방법 둘을 비교해달라고 했다. 후자는 ISR에 의해 선점당할 가능성이 있다고 말했고, 전자는 현재 CubeMX에 의한 제약에 따라 시스템 태스크만 시작시킬 수 없으며 태스크를 강제로 정지시키는 것도 시스템 태스크가 직접 수행해야하기 때문에 다른 태스크가 먼저 실행되면 초기화가 제대로 되지 않을 수 있다고 했다.

대신, 시스템 태스크의 초기화가 선행되어야 하는 태스크들에는 시그널을 받기 전까지 기다리는 코드를 넣으면 해결할 수 있다고 했다. 시그널을 주기 위해 FreeRTOS의 이벤트를 사용하면 된다고 한다. 이렇게 하니 각 태스크들이 자체적으로 인자를 수신하는 코드만 실행하고 핵심 로직 시작 전에 시스템 태스크의 초기화 이벤트를 기다리게 되었다.

# u8g2 c++ 래퍼 구현

드라이버들의 초기화를 시스템 태스크에서 수행하려고 했더니 gmg12864 드라이버를 여러 태스크에서 접근하고 있길래 그냥 싱글턴으로 전환했다. 싱글턴으로 전환하는 김에 u8g2 라이브러리를 C++로 교체해보았다. 나중에 알았지만, 핵심 로직은 모두 C로 작성되어 있었고, 이에 대한 접근을 클래스로 제공하는 정도였다. 그것도 아두이노를 위해 미리 작성해둔 클래스들이어서 그런 클래스들을 참고해 직접 만들기로 결정했다. 

핵심 함수들을 접근하게 해주는 클래스는 u8g2였고, 이를 상속받아 재정의하면 됐다. 콜백함수들은 C 스타일로 구현해야하므로 멤버 함수로 둘 수 없어 별도로 뺐고, 초기화에 필요한 간단한 코드들만 추가하여 싱글톤으로 제공할 수 있게 구현했다. 

# sdram DMA R/W 구현

블로그에 정리했던 코드를 그대로 가져와서 sdram 초기화를 구현했다. 오디오 데이터를 저장하기 위해 DMA를 쓰려고 했으나, SDRAM쪽에 DMA 설정이 누락되어 있었다. DMA1,2는 D1과 D2 도메인의 메모리와 페리퍼럴 간 전송을 담당하기 때문에 SDRAM과 SRAM 간 전송(mem to mem)을 지원하지 못한다. 그래서 MDMA를 써야한다. CubeMX에서 mdma를 설정한다고 해도 SDRAM쪽에 바로 추가가 되지는 않았다. 애초에 추가할 수 있는 페이지가 없었다. 그래서 이 부분을 AI한테 도와달라고 했고, SDRAM 초기화 코드 마지막에 mdma를 연결하는 코드를 추가해야함을 알았다. 

# 녹음 기능 구현

납땜이 모두 마무리 된 후에는 예전에 구현했던 오디오 패스스루 코드를 이식하는 것을 먼저 했다. CubeMX 설정을 일치시킨 후 입력 버퍼에 쌓인 데이터를 곧바로 출력 버퍼로 보내기 위해 DMA 콜백을 활용했다. 오디오 패스스루는 금방 구현되었지만, 트랙이 녹음 상태일 때 입력 버퍼에 쌓인 데이터를 SDRAM에 저장하는 과정이 까다로웠다.

우선 트랙의 상태 변화를 수신해야하므로, 기존에 가지고 있던 오디오 이벤트 큐로 수신하려 했다. 그러나 오디오 패스스루를 구현하기 위해 DMA 이벤트 큐에서 대기하고 있었으므로 이벤트를 즉시 수신하지 못했다. 이 문제는 이전에 디스플레이 큐를 메일박스로 운용하는 패턴을 적용해 해결했다.

그 다음으로는 패스스루와 녹음을 동시에 수행하면서 발생할 수 있는 지연 문제였다. 문제라기보다는 처리 흐름을 명확하게 이해하지 못한 점이었다. 녹음과 재생의 흐름은 이렇다. 

시간 t1부터 t2까지 녹음된 1개의 프레임은 입력 버퍼에 담겨져 있고 t2에 DMA 이벤트가 발생한다. 이 프레임은 출력 버퍼에 담기게 되고 복사가 완료되면 이를 스피커로 출력하게 된다. 이 때 트랙이 녹음중이라면, t1부터 t2까지 녹음된 1개의 프레임이 트랙에도 저장되어야 한다. 이해가 미흡했던 부분은 저장된 트랙이 곧바로 재생된다면 출력 버퍼에 녹음된 트랙의 프레임이 들어가야 한다고 생각했다. 하지만 **프레임 단위로 트랙의 상태를 수신하기 때문에** t1부터 t2까지 녹음 상태였다면 한 프레임 내에서 트랙의 상태가 변하진 않으므로 트랙에 저장된 데이터가 곧바로 출력 버퍼로 가진 않는다. t2부터 재생 상태로 된다면 t1부터 t2까지 녹음한 프레임이 곧바로 SDRAM에 저장되어 있고 그 후 t2부터 t3까지 녹음한 데이터와 트랙에 저장된 데이터가 믹싱되어 출력 버퍼로 넘겨지게 된다.
