# C와 C++ 코드 간 경계 처리

1. 문제

C 코드에서 C++ 키워드를 쓸 수 없다. 그러므로 C++ 코드를 작성하더라도 C 문법에 호환되게 해야한다. App 코드에서 C 문법에 호환되게 써야하는 영역은 RTOS 큐 메시지 전송, 수신 영역과 main.c에서 정의하는 ISR 코드다. 큐의 타입은 단순 구조체가 될 수 밖에 없으므로 C++ 코드로 정의한 enum class와 클래스 인스턴스를 구조체에 담을 수 있도록 변환해야한다. 

2. 분석

리팩토링 이전의 C 코드들에서 힌트를 좀 얻었다. 태스크에서 쓰던 구조체를 RTOS 큐 메시지 타입으로 사용하지 않고 새로운 구조체에 담아 전송했다. enum class와 클래스 인스턴스도 그 구조를 유지하여 전송하면 된다고 생각했다. 단, 서로 다른 타입으로의 캐스팅이 문제였다. C 문법에서는 서로 다른 enum 이라고 하더라도 타입 검사를 하지 않았지만, C++ 문법으로는 컴파일 에러를 낸다. 따라서, 송신측에서는 템플릿을 활용해 다양한 enum class를 정수(uint8_t)로 변환하여 메시지에 담고 큐에 전송하도록 했다. 수신측에서도 템플릿을 활용해 정수를 enum class로 역변환해 기대한 타입으로 만들었다. 이렇게 하니 RTOS 메시지 구조체의 이름들이 컨벤션없이 작성된 것을 느껴 'RtosMessage_*', 'RtosPayload_*', 'RtosEnumValue' 와 같이 접두사를 붙여 표현하여 의도를 명확히 만들었다. 

여기까지는 좋았는데, 런타임에 C++과 C의 경계를 통과하면서 타입 변경이 발생할 수 있다는 사실을 알았다. enum class A가 정수로 바뀌고, RTOS 메세지 큐를 통과한후 다시 enum class로 역변환될 때 enum class B로 바뀌도록 작성하면 코드상으로는 문제가 없지만 의도대로 구현된 것이 아니게 된다는 것을 알았다. 이러면 해당 정수값에 대응되는 enum이 없는 경우에도 에러가 발생할 수 있다. 이 문제에 대해 AI에게 물어보았다.

3. 가설 검증

AI는 경계 통과 이후 값의 유효성에 대해 다음과 같이 답했다.

- 값이 연속적이라면 범위를 검사하면 된다. 

    ID와 같은 enum들은 0 ~ COUNT의 범위내에 모든 enum들이 있기 때문에 이렇게 검사하면 변환된 값이 유효한지 판단할 수 있다. 그러나 MenuIconEncoding처럼 모든 값이 연속적이지 않은 enum class도 있기 때문에 이 방법이 완전한 해결책이 될 수 없다고 판단했다.

- switch로 enum 검사하기

    각 enum마다 switch문을 갖는 검증 함수를 만들어야 하므로 그다지 좋은 방법이 아니라고 생각했다. enum에 변경이 발생하면 검증 함수도 수정해야하는 비용이 생기기 때문에 좋지 않다고 생각했다.

- 모든 enum이 저장된 array에 enum 값이 존재하는지 순회하며 확인하기

    이 방법은 enum class를 정의한 이후 이 enum들을 모두 배열에 넣어두고 그 배열을 순회하여 값을 찾기 때문에 검증이 무조건 된다.
    그러나 UiStateMachine::Id와 같이 enum 개수가 많다면 배열의 크기도 커져서 메모리를 약간은 차지하게 되므로 차선책이 된다고 생각했다. 

위 세 가지 가정 모두 정수 값이 enum class 내에 존재하는지를 검사한다. 그러나 경계를 통과하면서 다른 타입으로 변환되었지만 값 자체는 enum class에 존재해서 에러를 내지 않을 수도 있다. 그러므로 변환할 때 원본 타입대로 변환하는 코드를 짰는지는 검사하지 못한다.

4. 해결

C 문법에는 타입을 저장하는 기능은 없다. 그러므로 C/C++ 경계를 통과하면서 메시지 내에 타입을 담아 전송하도록 구현하는 것은 어렵다고 판단했다. 그래서 값의 유효성을 검사하는 방법을 구현하지는 않았고, 메시지 구조체 멤버명에 컨벤션을 따라 작성하도록 함으로 암시적인 규칙을 드러냈다. rtos_enum_value_{원본 타입}과 같이 구조체를 작성해둠으로 원본 타입을 유추할 수 있도록 했다.

5. 결과

아직 하드웨어 테스트를 해보진 않았다. 컴파일 에러는 없었고 빌드도 정상적으로 이뤄졌다.

# 그 외 리팩토링 결과

각 StateMachine을 객체화하였고, State들도 상속을 통해 재정의하여 간단하게 작성할 수 있도록 했다. StateMachine이 3개나 등장하므로 나중에 공통 StateMachine도 구현해야한다.

기존에 PanelSlot~으로 작성되었던 union 타입을 std::variant로 개선했다. Page 클래스 내에서 variant를 관리하게 수정하였고 Ui 정의 생성자도 단순해졌다.

각 상태를 별도의 .h, .c파일로 분리하여 구현했는데 상태를 객체화시킴에 따라 .c파일이 필요없어졌다. 기존에는 .c에 상태 구조체 인스턴스를 만들고 .h에서 extern으로 노출시켰지만, 이제는 .hpp에 상태 정의만 하고, *_pointer_map.cpp에서 상태 클래스 인스턴스를 선언함과 동시에 EnumMap에 포함시키는 방법을 써서 인스턴스 관리를 단순하게 만들었다. 

파라미터도 구조체 대신 클래스로 개선하여 여러 유틸 함수들을 멤버 함수로 개선하였다.

개발 보드가 도착했는데 아직 납땜은 못했지만 stlink 디버깅 테스트에는 성공했다. 오늘 핀헤더 소켓이 오면 내일 만능기판에 납땜하고 회로 구성을 할 계획이다.
